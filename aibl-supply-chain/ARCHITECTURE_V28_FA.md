# قرارداد معماری

## حدود مالکیت داده

یک رایانه اتاق کنترل، نویسنده اصلی SQLite است. فایل‌های Excel روی شبکه منابع ورودی‌اند؛ HTML و فایل‌های مخاطبان خروجی تبادل‌اند. سرویس API یا سرور مشترک اضافه نشده است. تمام لاگ‌های جدید مسیرهای مرکزیِ اصلاح‌شده در SQLite هستند. جدول audit تاریخیِ پروفایل‌های رمزگذاری‌شده قبلی حذف نشده است. فایل‌های سابق کاربر پاک یا بازنویسی نمی‌شوند. استفاده مستقل از ماژول شخصی روی رایانه‌های دیگر، بدون مسیر برگشت به اتاق کنترل، معادل ثبت مرکزی فعالیت نیست؛ این بسته همگام‌سازی خودکار تاریخچه چند رایانه را ادعا نمی‌کند.

## لایه‌ها و سطح رکورد

| جدول | سطح رکورد / قرارداد |
|---|---|
| wh_file | یک نسخه یکتای فایل با SHA-256، اصل بایت‌ها، اندازه، نام؛ یکتایی بر محتوا |
| wh_ingest | هر دریافت فایل در یک اجرا؛ دریافت تکراری قابل مشاهده، بدون تکثیر اصل فایل |
| wh_sheet | مشخصات شیت، وضعیت hidden، ستون‌ها، سلول‌های ادغام‌شده، شمار ردیف غیرخالی |
| wh_raw_row | فایل + شیت + شماره فیزیکی ردیف؛ آدرس، نوع، سبک، متن خام، فرمول و مقدار cache هر سلول |
| wh_business_record | رکورد هر منبع در سطح فیزیکی، با کلیدهای ثبت سفارش، سفارش، متریال و درخواست؛ هیچ JOIN چندبه‌چند خودکار ندارد |
| wh_measure | فایل + شیت + ردیف + نوع مبلغ؛ Decimal به شکل TEXT، ارز و اعتبار مقدار؛ جمع در Python Decimal و فقط داخل همان نسخه و ارز |
| wh_frame / wh_frame_row | نسخه جدول staging، استاندارد یا mart؛ نام و نوع ستون، ترتیب، ایندکس و مقادیر با codec نوع‌دار |
| wh_run | شروع، پایان، تاریخ مرجع، نسخه برنامه، وضعیت اجرا و خطا |
| wh_issue | محل و نوع مسئله؛ سلول فرمول خراب، ردیف بی‌شناسه، تعارض و موارد نیازمند بررسی |
| wh_audit | لاگ اجرا و تغییر تنظیمات با قبل/بعد، انتخاب شیت، مخاطب گزارش، ثبت خروجی و پیش‌نویس |
| wh_config | تنظیمات فعال مرکز مخاطبان با شماره نسخه و قفل خوش‌بینانه |
| wh_current | اشاره‌گر آخرین گزارش موفق؛ اجرای شکست‌خورده جایگزین آن نمی‌شود |

این مدل، آرشیو ورودی و martهای عملیاتیِ نسخه‌دار دارد؛ ادعای ساخت مدل ستاره‌ای کامل همه فرایندهای سازمان یا SCD2 موجودیت‌های فاقد کلید پایدار را ندارد. تاریخچه فایل و اجرای منبع برای بازبینی نگه‌داری می‌شود. برای تحلیل تغییرات یک موجودیت بین روزها باید کلید کسب‌وکار آن منبع تأیید شود؛ شماره ردیف اکسل به‌تنهایی کلید پایدار نیست. تغییرات میان دو نوبت دریافت اکسل که در هیچ فایل ورودی نمانده‌اند قابل بازسازی نیستند.

## انتشار و تراکنش

اصل فایل پیش از تفسیر ثبت می‌شود. رکورد خام هر شیت در یک تراکنش نوشته می‌شود. شکست تفسیر، داده خام را حذف نمی‌کند. فریم استاندارد پیش از استفاده خط لوله ذخیره و بازخوانی می‌شود؛ mart نهایی نیز پیش از ساخت گزارش ذخیره و بازخوانی می‌شود. اشاره‌گر گزارش تنها پس از پایان موفق اجرا به‌روزرسانی می‌شود. پوشه‌های خروجی و SQLite یک تراکنش توزیع‌شده ندارند: شکست خروجی فایل ممکن است فایل نیمه‌کاره یا بدون رسید ایجاد کند؛ اجرای ناموفق منتشر نمی‌شود و باید مجدداً اجرا شود. پروفایل رمزگذاری‌شده و SQLite نیز اتمیک مشترک نیستند؛ ثبت همه عملیات بیرون از برنامه یا بین چند رایانه تضمین نشده است.

ثبت تنظیمات کلاستر و قبل/بعد آن در یک تراکنش BEGIN IMMEDIATE انجام می‌شود. ورودی مخاطبان قبل از commit کامل اعتبارسنجی می‌شود. ساخت پیش‌نویس Outlook در مرحله ارسال نیست. گزارش‌ها به سطح داده مجاز همان فرد یا کدهای صریح تحت پوشش محدود می‌شوند؛ ادعای احراز هویت، RLS دیتابیس یا محرمانگی در برابر مدیر سیستم ندارد. دسترسی فایل SQLite باید با ACL سیستم‌عامل محدود شود؛ فایل SQLite مرکزی رمزگذاری داخلی ندارد، درحالی‌که فایل‌های شخصی قبلی همچنان رمزگذاری می‌شوند.

## کنترل‌های مهندسی

- foreign_keys=ON، synchronous=FULL، timeout اتصال ۳۰ ثانیه، قفل نویسنده سیستم‌عامل، پارامترگذاری SQL.
- طرح دارای wh_meta و user_version است؛ انتخاب دیتابیس نامرتبط متوقف می‌شود. این نسخه اولین طرح wh است و مهاجرت دیتابیس ناشناخته انجام نمی‌دهد.
- هیچ مقدار Decimal با SQLite SUM که ممکن است به float تبدیل شود جمع نمی‌شود. محاسبات قدیمی موتور گزارش هنوز pandas/float هستند؛ تطبیق مالی دقیق از wh_measure قابل بررسی است.
- مقدار مجهول و صفر واقعی متمایزند. فرمول اکسل در Python اجرا نمی‌شود؛ مقدار cache استفاده و نبود آن ثبت می‌شود. متن فایل منبع به عنوان کد اجرا نمی‌شود.
- ردیف‌های hidden خوانده می‌شوند؛ شیت hidden نیز آرشیو می‌شود. شیت خلاصه بدون امضای تراکنش وارد جدول تراکنش FX نمی‌شود.
- نسخه پشتیبان با SQLite Backup API ساخته می‌شود. عملیات نگه‌داری/پاکسازی خودکار تاریخچه وجود ندارد؛ سیاست retention باید با سازمان تعیین شود.
- برای فایل‌های بزرگ، بایت‌های فایل، مدل XML و فریم‌ها در حافظه‌اند. این پیاده‌سازی برای ورود batch روی رایانه سازمانی است؛ آزمون ظرفیت داده واقعی چندساله انجام نشده است. قبل از افزایش حجم، زمان ورود، اندازه DB و RAM پایش شود.
