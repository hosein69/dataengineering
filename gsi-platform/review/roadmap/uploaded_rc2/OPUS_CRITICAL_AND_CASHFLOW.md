## ۱. بحرانی — فرمت واقعی SAP

Evidence Pack واقعی نشان داد فایل SAP **پنج شیت** دارد (`pr`, `pack`, `po`, `inbound`, `GR`) و هیچ‌کدام `Data` نیست — تنها شیتی که رجیستری می‌خواند. زنجیره سکوت این بود: شیت پیدا نمی‌شود → adapter بدون exception `{}` می‌دهد → `sap` جزو critical نیست → **صفر ردیف، و گیت رد می‌شود**.

دو اصلاح:

**الف) adapter هر دو قالب را می‌شناسد.** اگر شیت‌های `pr`/`po`/`pack`/`inbound`/`GR` باشند، مسیر native اجرا می‌شود؛ وگرنه همان مسیر تک‌شیتی `Data` با پیشوند `po.`. نام فریم‌های خروجی عوض نشده، پس `business_dwh`، چت‌بات و گزارش بدون تغییر کار می‌کنند.

**نتیجه معماری:** در قالب واقعی، PR و PO در دو شیت جدا هستند، پس **خلط هویت PR هدر با PR سند خرید ساختاراً ناممکن است**. F017 در این قالب اصلاً نمی‌تواند رخ دهد.

```
po_items:  KEY_PO=4500000001  KEY_PR=6500029999  SAP_PR_ITEM=90
           KEY_MATERIAL=9111111111  KEY_REG_FILE=664823825  KEY_ORDER=502805
```

دو پل بومی که تا امروز استنتاج می‌شدند، حالا از شاهد هم‌ردیف می‌آیند: `شماره پرونده` → `KEY_REG_FILE` و `Our Reference` → `KEY_ORDER`. (`Your Reference` مرجع فروشنده است و جدا می‌ماند.)
شیت `inbound` هم پل مستقیم SAP↔بارنامه می‌دهد: `شماره بارنامه` → `KEY_BL`.

**ب) شیت مفقود دیگر بی‌صدا نیست.** چک تازه `SOURCE_SCHEMA_CONTRACT_BROKEN` با شدت **BLOCK**: وقتی فایل پیدا شده ولی هیچ شیت موردانتظاری در آن نیست، انتشار متوقف می‌شود. «فایل اصلاً نبود» همچنان DEGRADED می‌ماند — این دو وضعیت متفاوت‌اند.

## ۲. بحرانی — رسید کالا و شمارش دوباره

شیت `GR` با ۳۸۰٬۹۰۹ ردیف بزرگ‌ترین مجموعه داده پروژه است و تا امروز خوانده نمی‌شد. ستون `Movement Type` تعیین می‌کند ردیف رسید است یا **برگشت رسید** — و برگشت همان مقدار را با معنای معکوس تکرار می‌کند.

فریم تازه `goods_receipts` با دانه `(Material Document, Material Doc.Item)`:

| ستون | معنا |
|---|---|
| `SAP_GR_DIRECTION` | `RECEIPT` / `REVERSAL` / `UNCLASSIFIED` |
| `SAP_GR_SIGNED_QTY` | تنها مقدار **جمع‌پذیر**؛ برای نوع حرکت ناشناخته `NaN` |
| `SAP_GR_QTY` | مقدار خام، در قرارداد **غیرجمع‌پذیر** علامت خورده |

```
جمع ساده  : 125      ← ۶۰ رسید + ۶۰ برگشت + ۵ ناشناخته
جمع علامت‌دار: 0.0    ← برگشت، رسید را خنثی می‌کند؛ ناشناخته وارد جمع نمی‌شود
```

حرکت ناشناخته علامت نمی‌گیرد، حدس هم زده نمی‌شود — همان اصلی که RC برای تعهد چندارزی دارد.

## ۳. کش فلو — جمع رفع تعهد روی همه نسخه‌های آرشیو (F023)

`totals_by_currency` روی کل `wh_measure` جمع می‌زد، بدون هیچ فیلتر run یا فایل. `wh_measure` آرشیو append-only است: هر نسخه ingest‌شده از فایل NTSW در آن می‌ماند. یعنی **مانده دیروز روی مانده امروز جمع می‌شد**.

اکنون:

| حالت | دامنه |
|---|---|
| پیش‌فرض | فایل‌های **اجرای منتشرشده** (`wh_current` → `wh_ingest`) |
| بدون انتشار | تازه‌ترین ingest هر منبع |
| `all_versions=True` | کل آرشیو، **عمداً** |

خروجی هر ردیف دو فیلد تازه دارد — `دامنه` و `نسخه‌های شمرده‌شده` — تا «کل آرشیو» هرگز با «مانده جاری» اشتباه نشود.

```
دو ingest از همان فایل با مانده ۵۰:
  scoped        → 50   (دامنه: published_run:…)
  all_versions  → 100  (دامنه: all_archived_versions)
```

## ۴. RES-1/2/3 از بازبینی قبلی

- `SWIFT_SENT` در `STAGES` ثبت شد (پیش‌تر emit می‌شد ولی از مدل فرایند بیرون می‌افتاد و پرونده `NO_STAGE_EVIDENCE` می‌گرفت).
- ستون همزاد `<TARGET>_IS_UNKNOWN` برای شش هدف مالی: «صفرِ نامعلوم» از «صفرِ واقعی» جدا شد، بدون تغییر قرارداد عددی legacy.
- `derive_coverage` که نوشته می‌شد و هیچ مصرف‌کننده‌ای نداشت، به دو چک `DERIVED_SOURCE_COVERAGE` و `UNKNOWN_COERCED_TO_ZERO` تبدیل شد.
