# HRPerf — داشبورد عملکرد منابع انسانی (نسخه ۳٫۳٫۰)

سنجش عملکرد بر پایه **علیت**، نه صرفاً همبستگی. مدل دو سطحی است، وزن‌ها
در داشبورد زنده تغییر می‌کنند، و خروجی هم پایگاه داده است هم Excel و
HTML و PDF و بسته ایمیل.

> ارزیابی کامل پکیج قبلی و ده ایراد آن در `ARZYABI_PACKAGE_GHABLI.md`.
> مبنای علمی کلاسترها و مقالاتی که بررسی شد در `RESEARCH_BASIS.md`.

از نسخه ۳، **کلاسترهای عملکرد از خروجی پکیج زنجیره تأمین (AIBL)** ساخته
می‌شوند: پروندهٔ هر قطعه، لاگ رویداد، انطباق فرآیند، تعهد ارزی و رسوب
گمرکی. هر کارشناس فقط روی **مرحله‌های حوزهٔ خودش** سنجیده می‌شود —
کارشناس حمل بابت تعهد ارزی امتیاز نمی‌گیرد و کارشناس بازرگانی بابت رسوب
گمرکی.

```bash
pip install -r requirements.txt
python -m hrperf.cli demo            # اجرای نمونه بدون شبکه
python -m hrperf.cli run             # اجرا روی input_files (کنار همین پکیج)
python app/run_dashboard.py          # داشبورد
python run_all_tests.py              # ۴۳۰ تست
```

### ارسال گزارش در لحظه — تب «✉️ ارسال گزارش»

پیوست‌ها را انتخاب کنید (اکسل، HTML، داشبورد داینامیک، نقشهٔ سیال)،
گیرندگان To و Cc را از فهرست پرسنلی همان اجرا بردارید، متن را ببینید و
بفرستید. نشانی‌ها **هرگز** لاگ یا ذخیره نمی‌شوند؛ انتخابگر نام و اداره
نشان می‌دهد و نشانی را نقاب‌دار تأیید می‌کند.

روی سیستمی که اتلوک ندارد، پروندهٔ `.eml` بگیرید و همان‌جا باز کنید.

**آیا متن ایمیل می‌تواند داینامیک باشد؟ نه.** هیچ کلاینت ایمیلی
جاوااسکریپت را اجرا نمی‌کند — نه اتلوک کلاسیک، نه اتلوک جدید، نه
وب‌میل. بدنهٔ ایمیل جدول‌محور و امن روی موتور Word ساخته می‌شود، با یک
بلوک `@media` که فقط اتلوک جدید (Chromium) می‌بیند؛ و گزارش داینامیک
**پیوست** می‌شود. جزئیات در `RELEASE_NOTES_V3_3_0_DISPATCH.md`.

### نظام طراحی «آکوا»

همهٔ خروجی‌ها — اکسل، HTML، داشبورد، ایمیل و نقشهٔ سیال — از یک منبع
رنگ می‌خوانند: `hrperf/report/aqua.py`. نسخهٔ یکسان همین فایل در پکیج
زنجیره تأمین هست، پس دو پکیج کنار هم مثل یک محصول دیده می‌شوند.

پالت آکوای سازمانی مبناست، با سه اصلاح **محاسبه‌شده** (بردر نامرئی،
دکمهٔ برند زیر حد کنتراست متن، متن ثانویه روی کارت) و دو افزوده که
پالت اصلی نداشت: طیف دسته‌ای برای نمودار، و حالت تاریک. جزئیات و
اعداد کنتراست در `RELEASE_NOTES_V3_2_0_AQUA.md`.

### استودیوی کلاستر — پلتفرم را خودتان بچینید

از تب «🧬 استودیوی کلاستر»:

* **فضای برداری** — هر شاخص یک بردار است (ستون امتیازهایش روی همه افراد).
  انسجام هر کلاستر و جای هر شاخص سنجیده می‌شود: آیا عضویتی که ما تعیین
  کرده‌ایم با رفتار داده می‌خواند؟
* **موتور کلاستر** — پیشنهاد جابه‌جایی، هم‌پوشانی، تفکیک و تغییر وزن،
  هرکدام **با دلیل عددی**، و دکمهٔ اعمال. موتور کلاستر را کشف نمی‌کند؛
  کلاستر یک قرارداد سازمانی است. فقط می‌گوید داده کجا نمی‌خواند.
* **جابه‌جایی و رنگ** — شاخص را بین کلاسترها ببرید (وزن هر دو کلاستر
  خودکار بازنرمال می‌شود و `diff` هر جابه‌جایی را نشان می‌دهد)، و رنگ
  هر کلاستر را انتخاب کنید.
* **سورس تازه، بدون کد** — یک ورودی در `sources.yaml`؛ فرم همان تب هم
  آن را می‌سازد.
* **نقشهٔ سیال** — یک HTML مستقل و متحرک: ذره‌ها را بکشید، رنگ عوض کنید،
  تم را برگردانید، و نمای جدولی را ببینید.

### پوشه ورودی کجاست؟

پکیج پوشه `input_files` را به این ترتیب می‌گردد و **اولین موردی که فایل
داده دارد** را برمی‌دارد:

1. متغیر محیطی `HRP_INPUT` — همیشه مقدم
2. پوشه‌ای که فرمان در آن اجرا شده
3. کنار خود پکیج (جایی که زیپ باز شده)
4. `HRP_HOME` (پیش‌فرض `~/.hrperf`)
5. `D:\HRPerf\input_files` — فقط روی ویندوز

خروجی، لاگ و پایگاه داده **کنار همان ورودی** ساخته می‌شوند. اگر داده‌ای
پیدا نشود، پیام خطا **هر مسیری را که واقعاً بررسی شده** فهرست می‌کند —
دیگر لازم نیست حدس بزنید کد کجا را گشته است.

مسیر صریح:

```bash
# ویندوز
set HRP_INPUT=G:\000\hru\input_files
# لینوکس/مک
export HRP_INPUT=/srv/hru/input_files
```

### کد پرسنلی با پیشوند (`GS-`)

کد یک نفر در سورس‌های مختلف یک شکل ندارد: `GS-1234`، `1234`، `1234.0`
(وقتی اکسل ستون را عددی خوانده)، `GS‑۱۲۳۴`. همه به **یک کلید متعارف**
تبدیل می‌شوند — ارقام، صفرچین تا ۸ رقم — همان قاعده‌ای که
`aibl/core/text.py::clean_employee_code` در پکیج زنجیره تأمین به‌کار
می‌برد، تا خروجی دو پکیج روی یک کلید به هم بخورد.

در گزارش، ستون **«کد پرسنلی»** همان شکلی است که می‌شناسید (`GS-1234`)؛
کلید متعارف فقط برای اتصال است. دو محافظ: کلید بدون رقم (مثل `AHMADI`)
حذف نمی‌شود، و اگر دو **پیشوند متفاوت** روی یک شماره بیفتد
(`GS-1234` و `IK-1234`) ادغام اعلام می‌شود تا اگر واقعاً دو نفرند،
اصلاح شود.

نقشه سازمانی (`organization_map.json`) را کنار همان سورس‌ها بگذارید؛
بدون آن همه در یک «گروه همتای عمومی» می‌افتند و کارشناس ترخیص با
کارشناس اعتبارات مقایسه می‌شود.

### ۱٫۱ ورود مستقیم و غیرمستقیم

هر شاخص در `model.yaml` اعلام می‌کند چگونه وارد کلاستر می‌شود:

- `entry: direct` — مقدار مستقیماً از سورس می‌آید.
- `entry: derived` — با فرمولی از شاخص‌های دیگر ساخته می‌شود
  (`formula:`)، مثل `A/E` و «سختی مورد انتظار».

### ۱٫۲ نقش کاری — «کارشناس» یک شغل نیست، هفت شغل است

| نقش | اداره | نمونه شاخص اختصاصی |
|---|---|---|
| کارشناس خرید خارجی | خرید خارجی | سفارش‌های یکتا، خطای بزرگ |
| کارشناس ثبت سفارش | ثبت سفارش | نرخ بارنامه باز، تکمیل |
| کارشناس اعتبارات | اعتبارات | زمان اصلاح، هزینه دوباره‌کاری |
| کارشناس رفع تعهد ارزی | رفع تعهد | Reject باز، تکمیل |
| کارشناس ترخیص | ترخیص | پرونده‌های یکتا، زیر ۲۴ ساعت |
| کارشناس کنترل اسناد | کنترل اسناد | FPY، A/E، موفقیت اولین اصلاح |
| کارشناس بازرگانی | بازرگانی | خطای بزرگ، ارزش سفارش |

سختی کار، مخرج شاخص‌ها و چرخه زمانی این هفت نقش با هم فرق دارد، پس
**شاخصی که برای نقشِ یک فرد بی‌معناست اصلاً محاسبه نمی‌شود** — «نرخ
بارنامه باز» برای کارشناس اعتبارات امتیاز نمی‌سازد.

### ۱٫۳ گروه همتا — چه کسی با چه کسی مقایسه می‌شود

مقایسه فقط درون `(مدیریت، اداره، نوع کار)` انجام می‌شود. اگر گروه از
حد نصاب (پیش‌فرض ۴ نفر) کوچک‌تر باشد، یک پله بالا می‌رود و **همین صعود
در خروجی ثبت می‌شود**، تا خواننده بداند مقایسه در چه سطحی بوده است.

### ۱٫۴ انقباض — چرا نمونه کوچک رتبه اول نمی‌شود

واریانس مقدار هر فرد دو بخش دارد: نویز نمونه‌گیری و تفاوت واقعی.

```
Var(xᵢ) ≈ σ²/nᵢ + τ²      ⇒   k = σ² / τ²
x̂ = (nᵢ·xᵢ + k·μ) / (nᵢ + k)
```

`k` با رگرسیون انحراف مجذور روی `1/nᵢ` از خود داده برآورد می‌شود.
اثرش روی داده واقعی:

| مقدار خام | n | بدون انقباض | با انقباض |
|---|---|---|---|
| ۱٫۰۰ | ۲ | **۷۹٫۵ (رتبه ۱)** | ۵۳٫۷ |
| ۰٫۹۸ | ۱۲۰ | ۶۴٫۶ | **۷۳٫۱ (رتبه ۱)** |

### ۱٫۵ امتیاز مطلق، نه رتبه‌ای

امتیاز نسبت به توزیع مرجع با میانه و MAD ساخته می‌شود و با
`50 + 45·tanh(z/2)` به بازه ۵..۹۵ نگاشت می‌گردد. اگر کل تیم بهتر شود،
امتیاز همه بالا می‌رود — چیزی که در رتبه درصدی ممکن نیست.

### ۱٫۶ تجمیع دو سطحی

```
cluster_score_c = Σ w_item_i · score_i        (نرمال روی آیتم‌های موجود)
performance     = Σ w_cluster_c · cluster_score_c
effective_weight_i = w_item_i × w_cluster_c
```

نبودِ یک شاخص، امتیاز را بی‌صدا پایین نمی‌آورد؛ در عوض **پوشش** پایین
گزارش می‌شود. `اطمینان = √(پوشش × شواهد)`.

### ۱٫۷ لایه علّی

DAG صریح اعلام می‌شود، مجموعه تعدیل با **معیار درِ پشتی** از همان DAG
استخراج می‌گردد، و اثر با باقی‌مانده‌گیری (Frisch–Waugh–Lovell) برآورد
می‌شود. خروجی، همبستگی خام را کنار اثر تعدیل‌شده می‌گذارد:

| از → به | همبستگی خام | اثر تعدیل‌شده | نتیجه |
|---|---|---|---|
| سختی → سرعت | −۰٫۵۴ | **۰٫۰۱** | همبستگی کاملاً مخدوش بود |
| سرعت → کیفیت | ۰٫۷۴ | ۰٫۲۶ | بخش بزرگی مخدوش بود |

**امتیاز منصفانه** = عملکرد واقعی منهای آنچه از شرایط کار (حجم، سختی،
تخصیص، سابقه) انتظار می‌رفت — تعمیم چندمتغیرهٔ A/E.

> ⚠️ با داده مشاهده‌ای علیت **اثبات** نمی‌شود. این اعداد «اثر تعدیل‌شده
> تحت فرض‌های DAG اعلام‌شده» هستند. ستون E-value می‌گوید یک مخدوش‌کننده
> اندازه‌گیری‌نشده چقدر باید قوی باشد تا نتیجه را برگرداند.

| کلاستر | وزن | چرا |

هر دو سطح در داشبورد قابل تغییرند و پس از هر تغییر بازنرمال می‌شوند.

### فهرست گیرندگان ایمیل — پیکربندی محرمانه

نشانی کارکنان داده شخصی است و در سورس نگه‌داری نمی‌شود. ترتیب اولویت:

```
۱) HRP_EMAIL_TO="a@example.invalid;b@example.invalid"
۲) HRP_RECIPIENTS_FILE=/secure/recipients.yaml
۳) $HRP_HOME/recipients.yaml
۴) HRP_EMAIL_FROM_HR=1   ← از جدول پرسنلی همین اجرا
```

بدون پیکربندی، ساخت گزارش کار می‌کند ولی **ارسال با خطای صریح متوقف
می‌شود**.

**گزینه ۴ (توصیه‌شده).** ستون ایمیل جدول پرسنلی همین اجرا منبع گیرندگان
می‌شود (`email` / `Email` / `HR_EMAIL` / `ایمیل` / …). چون همان جدولی است
که امتیازها از آن ساخته شده‌اند، فهرست هرگز کهنه یا ناهم‌گام نمی‌شود و
پرسنل غیرفعال خودکار حذف می‌شوند.

| متغیر | پیش‌فرض | کار |
|---|---|---|
| `HRP_EMAIL_FROM_HR=1` | خاموش | فعال‌سازی این مسیر |
| `HRP_EMAIL_HR_ROLES` | `مدیر,رئیس,مسئول` | فیلتر روی `role` |
| `HRP_EMAIL_HR_MANAGEMENTS` | — | فیلتر روی `management` |
| `HRP_EMAIL_HR_DEPARTMENTS` | — | فیلتر روی `department` |
| `HRP_EMAIL_HR_MAX` | — | سقف تعداد گیرنده |

فیلترها با هم AND می‌شوند. فقط پرسنل **فعال** و نشانی‌های معتبر انتخاب
می‌شوند، و در خروجی گزارش فقط **تعداد** گیرنده ثبت می‌شود
(`ReportResult.email_recipients`) — هرگز خود نشانی‌ها.
