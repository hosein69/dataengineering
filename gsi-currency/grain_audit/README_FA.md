# ممیزی دانه‌بندی، افزونگی و کلیدها (GSI)

این اسکریپت همه سورس‌ها را با آداپترهای خود اپ می‌خواند و یک فایل Excel می‌سازد که نشان می‌دهد کجا
دانه‌بندی، کلید کسب‌وکار، کلید اصلی یا افزونگی ستون‌ها ایراد دارد. فقط می‌خواند:

* فایل‌های سورس فقط خوانده می‌شوند.
* هر چیزی که آداپترها معمولاً در انبار داده می‌نویسند، به یک انبار موقت داخل پوشه خروجی می‌رود و آخر کار پاک می‌شود.
* انبار داده اصلی (`warehouse.sqlite`) با حالت فقط‌خواندنی باز می‌شود و تغییری نمی‌کند.

## نصب

پوشه `grain_audit` را از zip بیرون بیاورید و **داخل پوشه اپ** بگذارید، کنار پوشه `gsi`:

```
F:\BI\T18\app\gsi\
F:\BI\T18\app\grain_audit\gsi_grain_audit.py
F:\BI\T18\app\grain_audit\grain_audit.ini
```

اگر پوشه اپ شما جای دیگری است، مسیرها را همان‌طور عوض کنید. فایل cmd لازم نیست.

## اجرا در PowerShell

```
cd F:\BI\T18\app
python .\grain_audit\gsi_grain_audit.py
```

اگر اپ را با `.venv` اجرا می‌کنید:

```
cd F:\BI\T18\app
.\.venv\Scripts\python.exe .\grain_audit\gsi_grain_audit.py
```

مسیر سورس‌ها همان است که اپ استفاده می‌کند. اگر فرق دارد، فقط `grain_audit.ini` را ویرایش کنید.
با `mart = yes` (پیش‌فرض) جدول تخت هم با مرحله‌های اپ ساخته و سنجیده می‌شود؛ چند دقیقه طول می‌کشد.
برای اجرای سریع‌تر: `mart = no`.

## خروجی

در `grain_audit\output\`:

* `GSI_GRAIN_AUDIT_<تاریخ>.xlsx`: همین فایل را بفرستید.
* `GSI_GRAIN_AUDIT_<تاریخ>_summary.txt`: خلاصه متنی همان یافته‌ها.
* `GSI_GRAIN_AUDIT_<تاریخ>_graph.html`: گراف آفلاین. هر ستونی که در یک سفارش بیش از یک مقدار دارد، با احتمالش
  و بازه اطمینان ۹۵٪، به فایل‌های کدی که آن را می‌خوانند وصل است. رنگ می‌گوید مقدارها در خروجی ماند (سبز)، از دست
  رفت (قرمز)، جایی برای ماندن ندارد (کهربایی) یا طبق قاعده نوشته‌شده یکی شد (خاکستری). جای احتمالی رخداد تازه: ستون
  قرمز یا کهربایی با درصد بالا، در فایل‌هایی که خط بیشتری به آن‌ها می‌رسد. گراف هیچ مقدار داده‌ای ندارد.

خروجی نمونه کلیدها را دارد (مثلاً شماره سفارش یا بارنامه). اگر نمی‌خواهید مقدار واقعی دیده شود،
در ini بنویسید `mask_keys = yes`؛ آن وقت به‌جای هر کلید یک کد درهم می‌آید که باز هم برای مقایسه کافی است.

## برگه‌های فایل

| برگه | چه چیزی را نشان می‌دهد |
|---|---|
| 0_خلاصه | همه یافته‌ها با شدت (بحرانی، بالا، متوسط، پایین)، تعداد و نمونه |
| 1_فایل_و_شیت | فایل انتخاب‌شده هر سورس، فایل‌های اضافه با همان الگو، شیت مورد انتظار هست یا نه |
| 2_هدرها | هر ستون فایل خام: بی‌نام، تکراری، همیشه خالی، هم‌محتوا با ستون دیگر |
| 3_دانه_فریم | هر فریم اپ در برابر کلید اعلام‌شده‌اش: کلید ناقص، کلید تکراری، تکراری با محتوای متفاوت |
| 4_کلید_کسب‌وکار | شکل مقدارهای هر کلید (سفارش، متریال، بارنامه، ثبت سفارش، PR، PO، کارمند) و مقدارهایی که با نرمال‌ساز مرجع اپ عوض می‌شوند |
| 4_هم‌پوشانی_سورس‌ها | کلیدهای مشترک دو سورس، دقیق و با نرمال‌سازی شل |
| 5_جدول_انبار | ردیف‌هایی که به‌خاطر کلید تکراری یا کلید ناقص در جدول واقعیت انبار نمی‌نشینند |
| 6_جمعیت | دانه ردیف‌های گزارش: سفارش با چند ثبت سفارش، رابطه بی‌شاهد بارنامه × متریال، ردیف تکراری |
| 7_ستون_جدول_تخت | برای هر ستون جدول تخت: دانه اعلام‌شده، دانه واقعی، خالی، ثابت، هم‌محتوا، خطر جمع چندبرابر |
| 8_انبار | نسخه باز تکراری در انبار، ناهمخوانی موجودیت و بعد، کاردینالیتی رابطه‌ها، پنج اجرای آخر |
| 9_خطاها | اگر بخشی از خود اسکریپت خطا داد (بقیه بخش‌ها ادامه می‌دهند) |
| 10_فروریختگی | برای هر فریم جزئی و فریم تجمیعی آن (مثلاً ردیف‌های کارشناسان → main و inventory، با کلید سفارش×متریال و با کلید سفارش) و هر کلید اعلام‌شده در source_keys.yaml: سهم گروه‌هایی که ستون در آن‌ها بیش از یک مقدار دارد («احتمال چندمقداری») و اینکه خروجی همه مقدارها را نگه داشته (ستون *_ALL، *S_ALL، شمارش یا فهرست با «،» / «|») یا «یک مقدار نگه داشته شد». مرتب با ریسک = احتمال × ردیف اثرپذیر، با نمونه کلید |
| 10_فروریختگی_جفت‌ها | خلاصه هر جفت فریم: چند ستون سنجیده شد و کدام ستون‌ها فرو می‌ریزند |
| 11_واژگان | هر مقدار خام ستون‌هایی که با واژگان rulebook نگاشت می‌شوند (Order Status → part_state، Mode of Transport و ستون‌های روش حمل → transport_mode، Additional Data → مرحله، ستون‌های ارز)، تعداد، کد نگاشت‌شده و «نگاشت نشد» |
| 11_واژگان_خلاصه | برای هر ستون: مقدار نگاشت‌نشده، سهم ردیف و برای Order Status سهم Quantity In Part اثرپذیر |
| 11_نگاشت‌های_کد | فراخوانی‌های rulebook در آداپترها و اینکه در این بخش سنجیده شده یا نه |
| 12_تطبیق_مقدار | بازشماری مستقل از فایل کارشناسان در هر سفارش×متریال (هر محموله یک بار: Part No.، وگرنه BL، وگرنه Transport No.، وگرنه خود ردیف) در برابر ستون‌های MOGH_QTY_* خروجی inventory، main و جدول تخت؛ برابر، متفاوت، خالی در یک طرف و نرخ ناهمخوانی |
| 12_تطبیق_بارنامه_وضعیت | بارنامه‌ها (فقط A-Z و 0-9) و Order Statusهای فایل کارشناسان که در ستون‌های CANONICAL_BL، KEY_BL، MOGH_BL_NO، MOGH_BLS_ALL (یا ستون‌های وضعیت) خروجی نیامده‌اند؛ جدا برای بارنامه معتبر و ردشده در rulebook |
| 12_تطبیق_منبع | کدام خروجی‌ها مقایسه شدند؛ جدول تخت منتشرشده فقط‌خواندنی از انبار خوانده می‌شود و اگر نبود علتش همین‌جا نوشته می‌شود |
| 12_گراف_ستون‌ها | گراف ایستا: کدام فایل‌های gsi و app ستون‌های MOGH_BL_NO، MOGH_ORDER_STATUS، MOGH_TRANSPORT_MODE_CODE، CANONICAL_BL، KEY_BL و MOGH_QTY_* را می‌خوانند؛ یعنی عیب هر ستون کجا دیده می‌شود |

برای هر کدام از بخش‌های ۱۰، ۱۱ و ۱۲ یک ردیف «خلاصه بخش» (شدت اطلاع) در 0_خلاصه و فایل txt هست.
قاعده بخش ۱۲ مستقل از کد تجمیع اپ است: ردیف‌های هم‌شناسه یک محموله‌اند (بیشترین مقدار)، وضعیت خالی یا
ناشناخته «نامشخص» است و اگر مقدار نامشخص باشد وضعیت‌های صفر خالی می‌مانند (صفر ساخته نمی‌شود).
در گمرک یک بار با Quantity In Part و یک بار خالص (منهای Customs Cleared Quantity) مقایسه می‌شود.

**افزوده دور ۱۰**
* «احتمال چندمقداری» بازه اطمینان ۹۵٪ ویلسون دارد: با چند سفارش کم بازه پهن است و با داده واقعی تنگ می‌شود.
* کاهش‌های عمدی (زودترین مهلت تعهد NTSW، درخواست تعیین‌کننده تخصیص) «یک مقدار طبق قاعده» گزارش می‌شوند نه فروریختگی
  (فهرست در `BY_DESIGN` داخل اسکریپت).
* 12_تطبیق_مقدار در دانه سفارش «مقدار سفارش» و «ارزش PI سفارش» را هم می‌سنجد: قلم (متریال + PR + قلم PR + PI فروشنده)
  که روی چند پارت تکرار شده یک بار شمرده می‌شود. جمع ساده روی ردیف‌ها سفارش چهارپارتی را چهار برابر نشان می‌داد.
