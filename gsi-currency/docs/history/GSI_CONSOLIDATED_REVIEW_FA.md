# گزارش بررسی، مقایسه و تحویل GSI

**نسخهٔ تحویل:** 29.8.2 — RC4 OPT2 H1 Consolidated

**تاریخ بررسی:** ۲۰۲۶/۰۹/۲۴

این گزارش بر خواندن فایل‌های پیوست، مقایسهٔ بایت‌به‌بایت سورس، بررسی لاگ بازخورد ویندوز و اجرای تازهٔ آزمون‌ها استوار است. گزارش‌های قدیمی داخل پکیج، مدرک تاریخی‌اند و نتیجهٔ اجرای این نوبت محسوب نمی‌شوند. تغییرات این تحویل ادامهٔ محصول موجود است و بازنویسی معماری یا جایگزینی قواعد مالی انجام نشده است.

## ۱. نتیجه و حدود تحویل

بستهٔ AUDIT2 مبنای تحویل انتخاب شد؛ اصلاحات AUDIT1 را در خود دارد و نسبت به آن هیچ فایل موجودی حذف نشده است. ایرادهای تازهٔ اجراکنندهٔ آزمون، قفل‌گذاری reset، چرخهٔ عمر اتصال SQLite و آزمون‌های ناسازگار با ویندوز/ترتیب اجرا اصلاح شدند. محصول به همراه سورس، آزمون‌ها، راهنمای شروع، گزارش تغییرات و شواهد جدید تحویل می‌شود.

**موفقیت آزمون نرم‌افزاری با پذیرش عملیاتی روی شبکهٔ سازمان یکسان نیست.** در این نوبت، Windows 11/Python 3.13.9 سازمان، اشتراک‌های واقعی SAP/NTSW/Oracle، Outlook واقعی و Workspace واقعی AnythingLLM در دسترس آزمون نبودند. فایل‌های Excel نمونه و گزارش‌های تاریخی داخل بسته، جایگزین آن مجموعهٔ ورودی واقعی نیستند. به همین دلیل production_certified برابر false باقی می‌ماند و پذیرش عملیاتی باز است.

## ۴. اصلاحات این نوبت و علت هرکدام

### ۴.۱. صحت اجراکننده و gate

- آزمون دارای entrypoint اسکریپتی با خود Python اجرا می‌شود؛ بقیه با pytest. نتیجهٔ «تستی جمع نشد» به‌جای اجرای تست قبول نمی‌شود.
- هر فایل آزمون فضای DWH موقت مستقل می‌گیرد و ریشهٔ پکیج در PYTHONPATH آن قرار می‌گیرد. دو اسکریپت قدیمی بدون این مسیر اصلاً قادر به import محصول نبودند.
- `run_all_tests.py` اکنون فایل‌های legacy_test را هم کشف می‌کند.
- حد پیش‌فرض زمان هر فایل در اجراکنندهٔ آفلاین از ۱۸۰ به ۶۰۰ ثانیه رسید؛ کندی همچنان با timeout گزارش می‌شود و موفقیت فرض نمی‌شود.
- exit غیرصفر، exception، تعداد ناقص آزمون مستقل، ردشدن آزمون داخلی یا موجودنبودن نتیجهٔ سورس/NTSW مانع پذیرش است. دانستن نام یک شکست، آن را از blocker بودن خارج نمی‌کند.
- وابستگی‌ها با requirements تحویل‌شده تطبیق می‌خورند؛ از جمله streamlit-sortables==0.3.1. در اجراکنندهٔ CMD/PowerShell، Python پوشهٔ .venv بر Python عمومی اولویت دارد.

### ۴.۲. reset و اتصال‌های SQLite

راهکار AUDIT2 برای خالی‌کردن دیتابیسِ غیرقابل‌حذف حفظ شد، اما سه خطرش بسته شد: reset اکنون همان قفل نویسنده را می‌گیرد؛ هنگام باقی‌ماندن فایل اصلی، WAL/SHM را حذف نمی‌کند؛ نام‌های SQL با quote درست پاک می‌شوند و عملیات DDL در transaction قرار دارد.

فایل قفل عمداً باقی می‌ماند، اما قفل سیستم‌عامل آزاد می‌شود. حذف فایل قفل در سیستم‌های مبتنی بر inode می‌تواند به دو قفل مستقل برای یک مسیر منجر شود. آزمون قدیمی «نباید فایل قفل بماند» به آزمون دقیق‌ترِ «قفل دوباره قابل اخذ است» تبدیل شد. آزمون فعالیت هم‌زمان نویسنده، حفظ داده و سلامت SQLite اضافه شد.

در `historical_store.py` context manager تراکنش اضافه شد: commit/rollback و سپس close قطعی. API عمومی connect حفظ شده است. اتصال خامی که مصرف‌کننده مستقیماً می‌گیرد همچنان مسئولیت بستن دارد. این اصلاح، کلاس مشخص نشت handle را پوشش می‌دهد؛ معادل تأیید همهٔ خطاهای WinError32 روی ماشین سازمان نیست.

### ۴.۳. پاسخ‌های هوش مصنوعی

AUDIT1 فقط helper وجود منابع را داشت. اکنون `ask_evidence` یک مسیر قابل استفاده برای مصرف سمت سرور است: query درخواست می‌شود؛ اگر metadata منبع خالی یا بی‌معنا باشد، متن ادعای تولیدشده کنار گذاشته می‌شود. با وجود منبع نیز verified=False باقی می‌ماند؛ citation می‌تواند ناقص یا نامرتبط باشد و صحت پاسخ را اثبات نمی‌کند.

این مسیر، جایگزین ناگهانی ask خام یا ویجت عمومی نشده است. Knowledge Desk داخلی همچنان مسیر بازیابی خود را دارد. بنابراین نه تضمین «توهم صفر» داده می‌شود و نه آزمون mock به اتصال زنده تعبیر می‌شود.

### ۴.۴. آزمون‌ها و تفاوت با تغییر محصول

- فایل تنظیمات آزمون هویت با json.dumps ساخته می‌شود تا بک‌اسلش مسیر ویندوز JSON را خراب نکند.
- دفتر سلامت هر آزمون مستقل است. اجرای معکوس نشان داد schema_gap آزمون قبلی به آزمون پوشش سورس بعدی نشت می‌کرد؛ قواعد واقعی «سورس نبود» و «ساختار سورس خراب بود» تغییر نکردند.
- آزمون قدیمی HTML، JSON را تا نام متغیر بعدی با regex می‌خواند؛ اضافه‌شدن متغیر MATERIAL_SUPPLY_DATA آن را می‌شکست. اکنون JSONDecoder دقیقاً همان payload را می‌خواند و وجود هر ۳۰۰۰ ردیف را بررسی می‌کند.
- آزمون فرآیند، تب و نمای flow_map را صریح تنظیم می‌کند و نبود Event Log را در خروجی بررسی می‌کند؛ انتظار عنوان متنی منسوخ حذف و با قرارداد فعلی جایگزین شده است. آزمون نمودار، ایمیل، Excel فارسی/RTL و migration backup حفظ شده‌اند.
- frozen suite مستقل و ۷۷ آزمون تکمیلی تغییر داده نشده‌اند. تغییرات آزمون‌های داخلی و محصول در patch تحویل قابل مشاهده‌اند.

محیط آزمون: Linux، CPython 3.12.14. فایل دقیق نسخه‌های وابستگی کنار سورس تحویل شده است.

عددهای بالا مستقل از یکدیگر جمع‌پذیر نیستند: برخی سناریوها در pytest، اجرای اسکریپتی و اجرای معکوس تکرار شده‌اند. شمارش checkهای اسکریپت‌ها نیز با تعداد test caseهای pytest یک واحد ندارد. هش ورودی آزمون، لاگ خام و XML خروجی برای بررسی مستقل همراه بسته هستند.

هشدارهای باقی‌ماندهٔ آزمون‌ها شامل بازگرداندن مقدار از چند تابع قدیمیِ تست و Mean of empty slice در نمودار نمونهٔ خالی است؛ شکست به‌عنوان warning پنهان نشده است.

## ۶. تفسیر بازخورد و TRIAGE

- feedback مربوط به release_channel قدیمی offline-diagnostic است؛ سه ZIP محصول با آن یک بیلد نیستند.
- خطای شناسایی فایل .py/.md به‌عنوان NTSW در نسخه‌های محصول پیوست قبلاً رفع شده بود. اجرای تازه در درخت محصول، هیچ‌کدام را منبع واقعی اعلام نکرد.
- ۴۳+۳۳ شکست معنایی در بیلد قدیمی صرفاً به‌دلیل شناخته‌شده بودن قابل چشم‌پوشی نبودند؛ معیار بستنشان، اجرای تازهٔ ۱۷۳+۷۷ موفق است.
- بعضی WinError32های انبار عملیاتی در FINAL از قبل با بستن اتصال رفع شده بودند؛ نتیجهٔ قدیمی دوباره به‌عنوان باگ تازه بازنویسی نشد. نشت مستقل در انبار تاریخی این نوبت اصلاح شد.
- صرف یکسان بودن exit=1 در دو ترتیب آزمون، نبود وابستگی به ترتیب را ثابت نمی‌کند. اجرای معکوس این نوبت نمونهٔ مشخص نشت دفتر سلامت را پیدا کرد و اصلاح آن آزموده شد.
- بازخورد قدیمی هیچ سورس سازمانی پیکربندی‌شده‌ای در env_keys_present نداشت. اجرای فعلی هم گواه refresh/publish واقعی سازمان نیست.

## ۷. استقرار و معیار پذیرش

۱. ZIP جدید در پوشهٔ مستقل باز شود؛ با پوشهٔ نسخهٔ قبلی مخلوط نشود. دیتابیس عملیاتی پیش از تعویض نسخه با سازوکار backup موجود پشتیبان‌گیری شود.

۲. محیط .venv مطابق requirements برقرار شود. فهرست نسخه‌های واقعاً آزموده‌شده در `requirements-validated.txt` است؛ این فهرست شاهد محیط Linux/Python 3.12 این بررسی است، نه گواه سازگاری تمام ترکیب‌های Windows/Python.

۳. مسیر دیتاورهوس از طریق GSI_DWH_PATH یا GSI_DATA_ROOT تعیین شود. پیش‌فرض موجود D:\GSI_DATA\warehouse.sqlite حفظ شده است. تغییر متغیر مسیر، دیتابیس قدیمی را خودکار جابه‌جا نمی‌کند؛ برای جابه‌جایی باید سرویس‌ها متوقف و از backup معتبر استفاده شود.

۴. مسیرهای واقعی GSI_* و تنظیمات سورس بر اساس محیط سازمان تعیین شوند. فایل تنظیمات حاوی مسیر ساختگی یا دادهٔ خام سازمانی در این تحویل اضافه نشده است.

۵. START_GSI.cmd برای UI؛ REFRESH_GSI_DATA.cmd برای refresh صریح؛ EXPORT_GSI_EXCEL.cmd برای خروجی snapshot؛ RUN_OFFLINE_DIAGNOSTIC.cmd برای شواهد پذیرش اجرا شوند. برای آزمون فقط نرم‌افزاری: `python run_all_tests.py`.

۶. پذیرش عملیاتی زمانی بسته می‌شود که همان بیلد روی ویندوز هدف، سورس‌های لازم را بخواند، quality gate بگذرد، snapshot جدید منتشر کند و خروجی با جمع‌ها/کلیدها/ارزهای مراجع واقعی تطبیق داشته باشد. مسیر ORDER/BL به شواهد اتصال واقعی نیاز دارد؛ هیچ کلید مفقودی حدس زده نمی‌شود.

۷. برای بازگشت، نسخهٔ قبلی و backup معتبر نگه داشته شوند. روی انبار فعال reset اجرا نشود؛ reset فقط با درخواست صریح و قفل انحصاری انجام می‌شود.
